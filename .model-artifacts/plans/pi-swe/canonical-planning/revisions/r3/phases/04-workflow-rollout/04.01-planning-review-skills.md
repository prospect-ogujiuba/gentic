# Subphase 04.01: Planning and plan-review skill contracts

Created: 2026-08-30
Purpose: Turn planning into the thorough architecture/review/revision workflow defined by the initiative spec.

## Goal and observable behavior

Invoking `swe-plan` for non-trivial work creates/continues one canonical initiative spec, plan index, phase/subphase contracts, applicability matrix, specialist findings, and plan-review loop; it stops with an explicit approval/readiness result and never implements.

## Dependencies

- Phase 03 complete.

## Expected files

- Rewrite `extensions/pi-swe/skills/swe-plan/SKILL.md`.
- Expand `extensions/pi-swe/skills/swe-review/SKILL.md` with distinct plan-review and implementation-review modes.
- Update `swe-orchestrate`, `swe-dsa`, `swe-tdd`, and `swe-diagnose` planning handoff language where needed.
- Extend skill-content assertions in `test/pi-swe.test.ts`.

## Implementation contract

1. `swe-plan` follows Specify → Classify → Draft phases/subphases → Specialist applicability/review → Plan review → Revise → Approve → mark first contract ready.
2. Require one exact topic, canonical path index, revision links, contract metadata/sections, dependency graph, traceability table, verification matrix, and open blockers.
3. Define compact trivial-work profile without todo-root canonical writes.
4. `swe-review plan` checks architecture, completeness, dependencies, DSA/TDD/specialists, migration/rollback, acceptance/verification, and developer executability; decision approve/request changes/return to spec.
5. Accepted specialist findings require plan revision incorporation before approval.
6. Use todo only to record/link approved contracts; planning still works without it.
7. Output only key artifact paths, decision, blockers, and next edit/review order.

## TDD boundary

Characterization first: skill inventory/namespaces remain. Red content assertions require canonical specs/plans paths, subphases, applicability, plan review, revision/approval, no implementation, and no canonical todo-phase writes. Test level: resource contract.

## Acceptance criteria

- A developer can follow the skill alone to produce execution-ready docs.
- Plan-review is clearly distinct from post-implementation review.
- DSA/TDD planning decisions feed contracts; plan-time TDD does not claim Red evidence.
- No peer extension internals or new `/swe-auto`/legacy namespace appears.
