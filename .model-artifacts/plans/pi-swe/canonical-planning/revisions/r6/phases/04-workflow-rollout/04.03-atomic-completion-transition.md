## Goal and observable behavior

A user or long-running agent invokes one completion action for the active reviewed contract. The action validates exact revision/hash, approval, verification, and implementation-review evidence; atomically marks the contract complete, clears or advances `manifest.activeContract`, recomputes readiness, and reports a concise human-readable status without renaming canonical files.

## Scope and non-goals

Scope includes the extension-local completion transition, guarded command/action surface, atomic persistence, status projection, primitive migration guidance, documentation, and focused tests. Do not implement autonomous execution loops, commit/push behavior, remote coordination, a generic workflow engine, or initiative finalization beyond recomputing existing readiness.

## Implementation contract

1. Define one request/result API for completing an exact contract, including topic, contract ID, expected plan revision, expected pre-completion contract hash, verification path and digest/identity, approving implementation-review path and decision identity, and a deterministic completion request ID derived from those immutable inputs.
2. Re-inspect canonical state immediately before mutation and apply guards in this order:
   - **Unfinished transaction first:** if a journal exists for the topic, recover or block before evaluating a new/repeated request.
   - **Exact already-complete identity second:** before requiring `activeContract`, if the indexed target is already `complete`, its stable path and expected pre-completion hash/plan revision match the recorded completion transaction, the same verification/review identities remain available and approving, and the request ID equals the durable completed request ID, return `already-complete` with the recorded next-state summary and perform no writes. This applies whether `activeContract` was cleared or advanced.
   - **Active mutation third:** only for a non-complete target, require `activeContract` to name the exact contract and reject absent/wrong pointers, stale plan/contract hashes, incomplete dependencies, missing/failed/partial verification, non-approve review, conflicting disposition, path escape, or unsupported schema.
   - A complete target with mismatched request/evidence/hash identity is a deterministic conflict, never idempotent success.
3. Extend the schema-v1 canonical contract index with an optional, backward-compatible top-level `completionRecords` object owned by `contracts.json`; update `CanonicalContractIndex`, its parser/inspector projection, diagnostics, and fixtures. It is bounded to at most 500 contract-ID keys (each existing bounded contract ID), with each value exactly:
   - `schemaVersion: 1`, `requestId: sha256:<hex>`, `planRevision: positive integer`, `contractPath`, `preCompletionContentHash: sha256:<hex>`;
   - `verification: { path, contentHash: sha256:<hex> }` and `review: { path, contentHash: sha256:<hex>, decision: "approve" }`;
   - `completedAt` timestamp and `nextState: { initiativeState, activeContractId: string|null, readyContractIds: string[] }`, with `initiativeState` limited to `executing|finalizing`, active/ready IDs required to exist in the index, ready IDs unique and bounded by the 500-contract limit.
   Contract path must equal the indexed path beneath the active `contractRoot`; verification/review paths must stay under `.model-artifacts/reports/<topic>/`; hashes/request IDs have fixed sha256 form; existing artifact-path/string bounds apply. Every record key must resolve to an indexed contract whose status is exactly `complete`; reject records on `pending`, `in_progress`, or `blocked` contracts, absent keys, unknown/invalid fields, duplicate/mismatched keys, or path/revision/evidence mismatches. The canonical reader must expose validated records so reload idempotency never depends on an uncleared journal or chat.
4. Prepare new `contracts.json` and `manifest.json` bytes in memory. Set the indexed contract status to `complete`, retain its stable path, add/replace only its exact `completionRecords[contractId]`, clear or advance `activeContract` according to explicit command semantics, and update initiative state without claiming finalization. Validate the record's `nextState` against this same prepared manifest/index snapshot: initiative state equals the prepared manifest; active ID equals its `activeContract` ID or null; and ready IDs exactly equal the readiness reducer's sorted output. Post-write inspection repeats these cross-state checks before commit. On later reload, `nextState` is an immutable historical snapshot: validate that referenced IDs still exist, but do not require it to equal legitimately advanced current state; `already-complete` reports recorded and current state separately. The prepared contract-index bytes therefore durably own the request/evidence/result identity used by the already-complete guard.
5. Persist both targets as one recoverable logical transaction with a fixed journal at `.model-artifacts/logs/<topic>/completion-transaction.json`:
   - Write/fsync each target-adjacent prepared file and target-adjacent preimage backup containing the exact current bytes; verify prepared/preimage hashes before journaling.
   - Write/fsync a bounded closed schema-v1 journal containing topic, request ID, `stage`, and for each role (`contract-index`, `manifest`): target path, prepared path/hash, preimage backup path/hash, and target-adjacent restore-temporary path. `stage` is exactly one of `prepared`, `contract-index-installed`, `manifest-installed`, `rollback`, `validated`, or `cleanup`. Persist every stage update through temporary-write, fsync, rename, and journal-parent fsync. Installation uses POSIX rename, which consumes its prepared source; no copy/hardlink is assumed.
   - Apply this per-role installation invariant: while a role's target has its preimage hash, its prepared path must exist and match the prepared hash; after the target has its prepared hash, its prepared path must be absent. Both backups remain present and verified through `manifest-installed`. Any other target/prepared combination blocks recovery.
   - `prepared`: manifest target is preimage with verified prepared path; contract-index satisfies either side of the per-role invariant because its rename may precede the next journal update. Normal execution renames contract-index prepared over target, fsyncs parent, then persists `contract-index-installed`. Recovery persists `rollback` before restoring.
   - `contract-index-installed`: contract-index target is prepared and its prepared path is absent; manifest satisfies either side of the per-role invariant because its rename may precede the next journal update. Normal execution renames manifest prepared over target, fsyncs parent, then persists `manifest-installed`. Recovery persists `rollback` before restoring.
   - `manifest-installed`: both targets have prepared hashes, both prepared paths are absent, and both backups verify. Re-inspect completion-record disposition and same-snapshot `nextState`. Success persists `validated`; failure persists `rollback` before restoring.
   - `rollback`: both backups remain present and verified; each target may have preimage or prepared hash after an interrupted install/restore. Never rename a backup. For each target, copy backup bytes to its recorded restore-temporary path, fsync/verify that temporary, rename it over the target, fsync parent, and retain the backup until both targets verify their preimage hashes. A restore temporary may be absent after its consuming rename or present only with the preimage hash; recreate it from the backup as needed. Any remaining prepared path may be present only with its prepared hash and is removed after both targets verify. Then remove restore/prepared/backups and delete the journal last with parent fsync. A crash at any point resumes `rollback` without losing either backup.
   - `validated`: both targets have prepared hashes, both prepared paths are absent, and canonical cross-state validation is committed. Persist `cleanup`; never roll back from `validated` or `cleanup`.
   - `cleanup`: verify both target prepared hashes and canonical cross-state validity; idempotently remove any remaining backups/restore temporaries, tolerating every absent/present cleanup subset when present artifacts match recorded hashes; fsync affected parents; delete the journal last and fsync its parent. A crash after `validated`, including partial artifact removal, resumes cleanup without requiring backups.
   - Recovery dispatches only by durable stage and these exact hash/presence combinations. `prepared`/`contract-index-installed` enter `rollback`; `manifest-installed` validates and advances or enters `rollback`; `rollback` restores; `validated`/`cleanup` finish committed cleanup. An impossible combination or missing/corrupt artifact required by the stage retains all remaining artifacts and enters explicit `blocked-recovery`. Never infer bytes from hashes alone.
6. Re-inspect after persistence/recovery. Report old/new disposition, completion-record identity, evidence paths, next ready contract(s), blockers, and intended next skill. Never report completion before journal cleanup and canonical validation.
7. Add a human-readable status projection through `/swe status` or completion output: contract ID, disposition, active/next contract, phase progress, and blockers. Do not encode state in filenames.
8. Revise the completion primitive: canonical contracts beneath an active manifest/contract index must never be renamed for status; `[COMPLETE]` remains a temporary legacy-only convention until migration is finished.
9. Preserve standalone operation, bounded retries, path confinement, existing public skills, and guidance-only orchestration outside the explicit completion action.

## Acceptance criteria

- One explicit action completes only the exact approved, verified, implementation-reviewed active contract.
- No success result leaves manifest and contract index disagreeing; injected interruption produces stage-defined verified rollback, stage-defined committed cleanup, or explicit blocked recovery before later mutation.
- Canonical contract filenames remain unchanged; human status is readable from `/swe status` and completion output.
- After journal cleanup and process reload, a repeated request matching the validated `contracts.json` completion record returns `already-complete` without writes after either active-pointer clear or advance; any identity mismatch returns a conflict.
- Stale hashes, missing/partial evidence, conflicting state, path escape, and unsupported schema yield deterministic no-write handoffs.
- Completion makes the correct next contract ready without starting autonomous work.
- The primitive no longer instructs canonical lifecycle work to use `[COMPLETE]` filenames.

## Migration and rollback

Treat existing `[COMPLETE]` names as legacy inputs during inspection/adoption. Do not bulk rename historical revisions. New active canonical revisions use stable paths and machine dispositions. Because POSIX installation renames consume prepared sources, target hashes determine whether each prepared path must exist or be absent. Pre-`validated` rollback preserves backups and installs separate restore temporaries so interruption cannot consume recovery bytes. Durable `validated` commits new state; later recovery only finishes idempotent cleanup. Missing/corrupt artifacts required by the current stage produce blocked recovery; never infer restoration from hashes.
