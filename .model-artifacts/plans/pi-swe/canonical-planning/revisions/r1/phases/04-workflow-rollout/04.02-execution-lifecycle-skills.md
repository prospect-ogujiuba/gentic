# Subphase 04.02: Execution, verification, review, and finalize skill contracts

Created: 2026-08-30
Purpose: Make approved subphase contracts the authoritative implementation and evidence boundary.

## Goal and observable behavior

Implementation skills refuse stale/unapproved contracts, execute one ready contract surgically, map tests/evidence back to acceptance criteria, and finalize only after initiative-level reconciliation.

## Dependencies

- `04.01`

## Expected files

- Update `extensions/pi-swe/skills/swe-implement/SKILL.md`.
- Update `swe-verify`, `swe-review`, `swe-finalize`, `swe-tdd`, `swe-dsa`, `swe-diagnose`, and `swe-orchestrate` contracts consistently.
- Extend skill-content assertions in `test/pi-swe.test.ts`.

## Implementation contract

1. `swe-implement` reads manifest, active approved plan, exact ready contract, linked findings, and current state; rejects stale revision/dependency/blocker and records scope changes through plan revision.
2. `swe-tdd` executes the contract's next observable behavior with runtime Red/Green/Refactor evidence.
3. `swe-dsa` during execution treats material design changes as return-to-plan, not silent contract edits.
4. `swe-verify` maps each check to contract acceptance criteria and planned verification, marking pass/fail/partial/gaps.
5. `swe-review implementation` compares diff/evidence to exact contract/revision and chooses approve/request changes/return to plan.
6. `swe-finalize` reconciles all outcomes, contract dispositions, approved deferrals, evidence, residual risks, and handoff.
7. `swe-orchestrate` reads canonical artifacts/state before chat and reports exact reads/write destination.
8. Preserve read-before-edit, surgical scope, bounded retries, and standalone operation.

## TDD boundary

Red resource assertions require approved active contract/revision language, acceptance-to-evidence mapping, return-to-plan rules, and finalize reconciliation. Characterize existing required headings and legacy-namespace omissions. Test level: resource contract.

## Acceptance criteria

- No execution skill treats any todo or plan filename as sufficient approval.
- Scope drift, stale revision, missing verifier, and conflicting changes yield deterministic handoff.
- Artifact kinds/paths are consistent across every skill.
- Chat output remains concise and artifact-oriented.
