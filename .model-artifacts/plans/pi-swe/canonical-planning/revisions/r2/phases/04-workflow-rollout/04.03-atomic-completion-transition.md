## Goal and observable behavior

A user or long-running agent invokes one completion action for the active reviewed contract. The action validates exact revision/hash, approval, verification, and implementation-review evidence; atomically marks the contract complete, clears or advances `manifest.activeContract`, recomputes readiness, and reports a concise human-readable status without renaming canonical files.

## Scope and non-goals

Scope includes the extension-local completion transition, guarded command/action surface, atomic persistence, status projection, primitive migration guidance, documentation, and focused tests. Do not implement autonomous execution loops, commit/push behavior, remote coordination, a generic workflow engine, or initiative finalization beyond recomputing existing readiness.

## Dependencies and entry inputs

- `04.02` complete with approved implementation review and current verification evidence.
- Valid active manifest, approved plan r2, `contracts.json`, exact active contract pointer, and repository runtime state.
- Existing lifecycle transition guards, canonical inspector, readiness reducer, and atomic repository-state persistence patterns.

## Implementation contract

1. Define one request/result API for completing the exact active contract, including topic, contract ID, expected plan revision, expected contract hash, verification path, and approving implementation-review path.
2. Re-inspect canonical state immediately before mutation. Reject stale plan/contract hashes, wrong or absent active contract, incomplete dependency state, missing/failed/partial verification, non-approve review, conflicting contract disposition, or unsupported schema.
3. Prepare both new documents in memory: set the indexed contract status to `complete`; retain its stable path; clear `activeContract` or select only the readiness reducer's lowest next ready contract according to explicit command semantics; update timestamps and initiative state without claiming finalization.
4. Persist `contracts.json` and `manifest.json` as one recoverable logical transaction: write/fsync a temporary file beside each target; durably record a transaction journal containing topic, target paths, pre/new hashes, and stage; rename in deterministic order; fsync affected parent directories; then clear the journal only after post-write validation. Canonical readers must detect an unfinished journal and block normal mutation until deterministic roll-forward or rollback completes.
5. Re-inspect after persistence. Report old/new disposition, exact evidence paths, next ready contract(s), blockers, and intended next skill. On interrupted write or post-write validation failure, recover from the journal or emit a deterministic recovery handoff without reporting completion.
6. Add a human-readable status projection through `/swe status` or completion output: contract ID, disposition, active/next contract, phase progress, and blockers. Do not encode state in filenames.
7. Revise the completion primitive: canonical contracts beneath an active manifest/contract index must never be renamed for status; `[COMPLETE]` remains a temporary legacy-only convention until migration is finished.
8. Preserve standalone operation, bounded retries, path confinement, existing public skills, and guidance-only orchestration outside the explicit completion action.

## TDD boundary

Red first at integration level: stale hash rejection, missing evidence rejection, simulated second-write failure with recovery, successful atomic completion, next-ready selection, stable filename assertion, idempotent retry, and primitive canonical/legacy guidance assertions. Green implements the smallest transaction/service and command wiring; refactor only after recovery and state invariants stay green.

## Acceptance criteria

- One explicit action completes only the exact approved, verified, implementation-reviewed active contract.
- No success result leaves manifest and contract index disagreeing; injected interruption produces a detectable journal and deterministic recovery before later mutation.
- Canonical contract filenames remain unchanged; human status is readable from `/swe status` and completion output.
- A repeated identical completion request is safely idempotent or returns an already-complete result without rewriting state.
- Stale hashes, missing/partial evidence, conflicting state, path escape, and unsupported schema yield deterministic no-write handoffs.
- Completion makes the correct next contract ready without starting autonomous work.
- The primitive no longer instructs canonical lifecycle work to use `[COMPLETE]` filenames.

## Migration and rollback

Treat existing `[COMPLETE]` names as legacy inputs during inspection/adoption. Do not bulk rename historical revisions. New active canonical revisions use stable paths and machine dispositions. Because two filesystem renames are not physically atomic, the durable journal makes the transition recoverable and reader-detectable. If validation or recovery fails, retain/restore pre-transition files and direct the user to the exact journal/recovery artifact rather than guessing state.
