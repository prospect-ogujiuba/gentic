# Subphase 03.01: Two-level lifecycle integration

Created: 2026-08-30
Purpose: Represent initiative planning/execution and active-contract progress without ambiguous flat states.

## Goal and observable behavior

Lifecycle APIs validate initiative transitions and contract transitions independently, then derive allowed orchestration actions from both. An executing initiative with a verifying contract remains valid; a plan revision moves initiative back to planning and invalidates the old active contract.

## Dependencies

## Implementation contract

1. Introduce explicit initiative and contract state unions/transitions while retaining a compatibility mapping for current flat runner states.
2. Define transition guards using readiness/gate outcomes, not output filename presence.
3. Model plan revision invalidation, contract defer/block, phase completion, next ready contract, finalizing, and complete.
4. Preserve bounded verify→implement and review→implement retry behavior per active contract; retry keys include plan revision/contract ID to prevent cross-contract leakage.
5. Keep blocked cases and human-request mapping, adding stale-plan, ambiguous-initiative, invalid-manifest, and dependency-blocked where necessary.
6. Ensure final completion references final handoff and all required contract dispositions.

## TDD boundary

## Acceptance criteria

- Flat-state compatibility cannot grant approval or readiness.
