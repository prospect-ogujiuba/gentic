# Subphase 02.02: Legacy adapter and initiative resolver

Created: 2026-08-30
Purpose: Preserve compatibility without allowing legacy todo plans to contaminate canonical state.

## Goal and observable behavior

Initiative resolution follows explicit topic → persisted marker → unique active manifest → optional todo canonical link → isolated legacy mode. Multiple or conflicting candidates return ambiguity; a legacy todo-phase plan returns `legacy-unverified` plus adoption requirements.

## Dependencies

- `02.01`

## Expected files

- Add/refactor resolver and legacy adapter near `extensions/pi-swe/src/orchestrate.ts` or `src/app/planning.ts`.
- Extend `test/pi-swe-lifecycle.test.ts`, `test/pi-swe-runtime.test.ts`, and capability tests only where optional todo links are involved.

## Implementation contract

1. Move current recursive regex scanning behind a `LegacyPlanInspector` with explicit source/status.
2. Define canonical and legacy result discriminants; callers cannot accidentally treat legacy as approved.
3. Implement deterministic resolution precedence and reject multiple active canonical manifests when no explicit topic exists.
4. Validate optional todo initiative link shape defensively; malformed/async peer data remains warning-only per current capability policy.
5. Define adoption guidance: create manifest, normalize into plan r1, validate DAG/applicability, complete plan review, then approve.
6. Preserve no-pi-todo behavior and existing skill/command namespace.
7. Do not write adoption artifacts automatically in this slice; expose the required next action.

## TDD boundary

Characterization Red: old todo phase remains detectable. New Red cases: canonical wins only when explicitly/persistently selected, mixed candidates are ambiguous, malformed canonical does not fall through, todo link enriches but does not approve, no peer remains valid. Test level: integration.

## Acceptance criteria

- Canonical inspector never reads `.model-artifacts/todo`.
- Legacy result cannot satisfy `plan-approved` or `contract-ready` types.
- Resolver reports candidate topics and remediation without dumping file contents.
- Compatibility behavior is covered before old locator code is removed or constrained.
