# Subphase 02.01: Canonical filesystem inspector

Created: 2026-08-30
Purpose: Load and validate one canonical initiative directly from its manifest and linked artifacts.

## Goal and observable behavior

An explicit canonical topic loads `specs/<topic>/manifest.json`, validates schema/identity/links, verifies required file existence and active hashes or freshness metadata, loads contract metadata, and returns a bounded readiness view. Malformed or stale artifacts produce diagnostics, never heuristic fallback.

## Implementation contract

1. Define a canonical inspector result containing source mode, manifest, contracts, gate evaluation, ready IDs, blockers, and diagnostics.
2. Resolve only the exact normalized topic manifest; do not recursively choose a matching plan.
3. Read bounded JSON/Markdown metadata with explicit UTF-8 and parse errors.
4. Validate every linked artifact path remains under the matching topic/kind and exists.
5. Recompute/validate plan integrity using Phase 01 domain functions.
6. Keep narrative Markdown opaque initially; executable contract metadata may come from a constrained sidecar/index representation defined in implementation without duplicating narrative requirements.
7. Return explicit unsupported-version and stale-link outcomes.

## TDD boundary

## Acceptance criteria

- Canonical result never depends on filename regex ordering.
- Errors are bounded and path-oriented.
- Inspector has no pi-todo dependency and accepts repository cwd/topic explicitly.
- Existing orchestration API remains temporarily adaptable for downstream migration.
