# Extension architecture consolidation implementation plan

## Objective

Implement the recommendations in the extension consolidation review while preserving all existing first-party tool names, slash commands, widget IDs, state formats, and workflow authority boundaries.

Source report: `.model-artifacts/system/reports/architecture/2026-09-22_0254-extension-consolidation-review.md`.

## Success criteria

1. No production source under `extensions/<a>/` imports `extensions/<b>/src/**`.
2. `pi-hud` consumes stable package-level Git and context snapshot contracts.
3. `pi-swe` and `pi-todo` share domain-neutral TUI mechanics without sharing lifecycle or persistence.
4. Artifact path safety and atomic publication have one implementation used by `pi-artifacts` and `pi-context`; SWE remains sole owner of `workflow.json`.
5. Scaffold behavior and generated bytes remain unchanged after templates leave `pi-catalog`.
6. The primitive framework is narrowed to a policy bundle, primitive scaffolding is retired, and `whimsical` no longer requires a runtime module.
7. Architecture checks prevent recurrence.
8. `npm run typecheck`, `npm run check`, `npm run check:commands`, `npm run check:performance`, and `npm test` pass.

## Non-goals

- Do not merge `pi-swe` and `pi-todo` state machines.
- Do not let `pi-artifacts` create or mutate SWE `workflow.json`.
- Do not combine `pi-context`, `pi-git`, and `pi-hud` into one extension.
- Do not change public tool/command schemas, persisted Todo events, SWE schema version, artifact paths, or HUD widget ID.
- Do not refactor third-party npm extensions.
- Do not create a generic catch-all `utils.ts`.

## Delivery strategy

Deliver as small, independently reviewable changes. Phase 1 is required first. After Phase 2, Phases 3–5 can proceed in parallel. Phase 6 is intentionally split into backward-compatible narrowing and a separately approved breaking rename.

```text
Phase 1: architecture guard
       |
Phase 2: snapshot contracts/services
       +------ Phase 3: docket-kit
       +------ Phase 4: artifact-store
       +------ Phase 5: scaffold relocation
                         |
                 Phase 6A: policy narrowing
                         |
                 Phase 6B: optional major-version rename
                         |
                 Phase 7: integration/release cleanup
```

## Phase 1 — Enforce extension dependency boundaries

### Design

Add a dedicated architecture check rather than overloading anatomy classification. Use TypeScript's import preprocessing or an equivalent deterministic parser to resolve static imports in extension production source.

Allowed:

- imports within the same extension;
- imports from package-level `src/contracts/**`, `src/services/**`, and `src/ui/**`;
- external packages and Pi APIs.

Rejected:

- an extension importing another extension's `src/**`, entrypoint, or resources;
- path traversal that resolves into a sibling extension.

Tests and scripts may import extension internals for focused testing; the production rule scans only extension source. Dynamic imports with statically known strings must also be checked.

### Tasks

- Add `scripts/check-extension-dependencies.mjs`.
- Add a focused test such as `test/extension-dependencies.test.ts` with valid, invalid, traversal, same-extension, package-service, and dynamic-import fixtures.
- Wire `check:dependencies` into `npm run check`.
- Introduce a narrow temporary allowlist containing only the four known HUD production importers:
  - `extensions/pi-hud/src/app/git-status.ts`
  - `extensions/pi-hud/src/app/snapshot.ts`
  - `extensions/pi-hud/src/pi/runtime.ts`
  - `extensions/pi-hud/types.ts`
- Make the check fail if an allowlisted import disappears without the allowlist being reduced, so the debt cannot become stale.
- Remove the allowlist completely in Phase 2.

### Exit criteria

- New cross-extension production imports fail CI.
- The allowlist contains no wildcard and no non-HUD file.
- `npm run check:dependencies` passes.

## Phase 2 — Extract Git and context snapshot contracts/services

### 2.1 Git snapshot service

Move reusable, Pi-registration-free behavior from `extensions/pi-git/src/app/snapshot.ts` into a package-level service, for example:

```text
src/contracts/git-snapshot.ts
src/services/git-snapshot/
  collect.ts
  parse.ts
  render.ts
  process.ts
```

The service owns typed snapshots, bounded subprocess execution, parsing, cancellation, deadlines, and public-field limits. `pi-git` continues to own the `git_snapshot` tool, `/pi-git`, and command-specific rendering. `pi-hud` consumes the typed snapshot/service and performs only HUD projection.

### 2.2 Context snapshot service

Extract the stable bounded projection consumed by HUD:

```text
src/contracts/context-snapshot.ts
src/services/context-snapshot/
  collect.ts
  pressure.ts
  numeric.ts
```

The service owns DTO validation, numeric normalization, usage collection, and pressure projection. `pi-context` retains configuration loading, lifecycle notifications, command handling, and report composition. `pi-hud` consumes one facade rather than context app/domain/config internals.

### Tasks

- Move contracts first and update tests to import package-level contracts.
- Move implementations without changing result shapes or limits.
- Update:
  - `extensions/pi-git/src/pi/register.ts`
  - `extensions/pi-hud/src/app/git-snapshot-service.ts`
  - `extensions/pi-hud/src/app/git-status.ts`
  - `extensions/pi-hud/src/app/snapshot.ts`
  - `extensions/pi-hud/src/pi/runtime.ts`
  - `extensions/pi-hud/types.ts`
  - `extensions/pi-context/src/app/**`
  - `extensions/pi-context/src/domain/**`
- Remove HUD's duplicate numeric guards; retain only presentation-specific formatting.
- Delete compatibility modules rather than leaving permanent forwarding layers unless an externally documented import requires one.
- Remove the Phase 1 allowlist and assert zero extension-to-extension production imports.
- Update READMEs to name the package-level contracts.

### Focused verification

```text
node --experimental-strip-types --test test/pi-git.test.ts
node --experimental-strip-types --test test/pi-context-*.test.ts
node --experimental-strip-types --test test/pi-hud-*.test.ts
npm run typecheck
npm run check:dependencies
npm run check:performance
```

### Exit criteria

- HUD has no import resolving under another extension.
- Git/context contract tests prove outputs and bounds are unchanged.
- Cancellation and shutdown still terminate pending Git work.
- Context snapshots remain content-safe and retain no prompt/message/path data.

## Phase 3 — Extract a shared `docket-kit`

### Design

Create a domain-neutral UI library, for example:

```text
src/ui/docket-kit/
  ansi.ts
  theme.ts
  status.ts
  frame.ts
  viewport.ts
  modal.ts
  types.ts
  index.ts
```

It may depend on `@earendil-works/pi-tui`, but it must not know about SWE work items, Todo events, workflow files, evidence, or lifecycle ownership.

### Extraction order

1. Move the identical formatting helpers from both `format.ts` files.
2. Unify theme/status-chip primitives.
3. Extract viewport, filtering, scrolling, selection, expansion, and keyboard mechanics from the similar modal implementations.
4. Define adapter types for row identity, label, status, detail lines, progress, and optional actions.
5. Convert SWE and Todo docket/modal modules into thin domain adapters.

### Tasks

- Add direct unit tests for ANSI width, truncation, frames, narrow widths, scrolling boundaries, empty lists, selection preservation, and keyboard actions.
- Preserve existing SWE/Todo snapshot tests as adapter-level regression tests.
- Keep all mutations in existing SWE/Todo services; shared UI emits intents only.
- Keep the shared kit free of session access, file I/O, Pi event registration, and timers.
- Update extension READMEs and anatomy notes.

### Focused verification

```text
node --experimental-strip-types --test test/pi-swe-docket.test.ts test/pi-todo-tui.test.ts
node --experimental-strip-types --test test/pi-swe-qualification.test.ts test/pi-todo-qualification.test.ts
npm run typecheck
```

### Exit criteria

- Duplicate `format.ts` implementations are removed.
- Shared modal mechanics have one tested implementation.
- SWE/Todo lifecycle, persistence, and mutation code remain separate.
- TUI and non-TUI output remain width-bounded and behaviorally equivalent.

## Phase 4 — Extract the artifact publication backend

### Design

Separate filesystem safety from Pi tool policy:

```text
src/contracts/artifact.ts
src/services/artifact-store/
  canonical-path.ts
  publish.ts
  filesystem-safety.ts
  hash.ts
  timestamp.ts
  index.ts
```

The store should expose typed operations, not arbitrary paths. Suggested operations:

- `publishInitiativeMarkdown(...)`
- `publishSystemMarkdown(...)`
- `publishSystemJson(...)` only to preserve `/pi-context json`
- `validateCanonicalArtifactReference(...)`

The model-callable `artifact` tool remains Markdown-only. `workflow.json` must be explicitly rejected by generic publication APIs.

### Tasks

- Move canonical segment/kind validation, timestamp naming, containment checks, symlink-parent checks, exclusive staging, atomic rename, directory sync, collision handling, and SHA-256 hashing from `pi-artifacts` into the service.
- Keep tool schemas and tool result shape in `extensions/pi-artifacts/src/pi/register.ts`.
- Migrate `extensions/pi-context/src/app/native-export.ts` to the shared store while preserving report locations and JSON support.
- Reuse canonical-reference validation from `extensions/pi-swe/src/app/artifacts.ts`, but keep SWE store, locks, revisions, and `workflow.json` writes untouched.
- Add contract tests that run the same safety matrix through artifact-tool and context-report adapters.
- Add a test proving neither generic store operation can create or overwrite `workflow.json`.
- Keep the `model-artifacts` injected policy synchronized with contract constants through a test or generated documentation fragment.

### Focused verification

```text
node --experimental-strip-types --test test/pi-artifacts.test.ts test/pi-context-native-pressure-export.test.ts
node --experimental-strip-types --test test/pi-swe-store.test.ts test/pi-swe-revision-context.test.ts
npm run check:model-artifacts
npm run typecheck
```

### Exit criteria

- One implementation owns artifact publication safety.
- Existing artifact and context-report paths remain byte-for-byte compatible in naming and content.
- Existing collision, traversal, symlink, size, and atomicity behavior is preserved.
- SWE remains sole writer of initiative `workflow.json`.

### Tasks

- Move `extensions/pi-catalog/templates/**` to `extensions/pi-commands/templates/**` with history-preserving renames.
- Update `TEMPLATE_ROOT` and containment checks in `extensions/pi-commands/commands/scaffold.ts`.
- Update `tsconfig.json`, resource/anatomy checks, docs, and tests referencing the old path.

- Preserve all generated bytes, target paths, rollback behavior, symlink checks, and supported kind names during this phase.

## Phase 6A — Narrow primitives into a policy bundle without renaming the extension path

This phase is backward-compatible at the package-filter level: keep `extensions/pi-primitives/` and the `pi-primitives` status key for now.

### Tasks

- Rename internal concepts from generic primitive host to policy bundle where this does not alter public paths:
  - `PrimitiveContext` → `PolicyContext`;
  - registry/report types → policy equivalents;
  - `prompt-policy.ts` and trigger engine remain shared policy infrastructure.
- Restrict the explicit registry to the three real policies:
  - `concise-output`;
  - `implementation-file-completion`;
  - `model-artifacts`.
- Delete `primitives/whimsical/index.ts`.
- Preserve one-release config compatibility by recognizing `whimsical` as a deprecated ignored name with a bounded warning; do not register or execute a no-op policy.
- Remove `primitive` from `/scaffold` supported kinds, completions, templates, and plugin guide. Treat this as a documented product-surface removal and call it out in the changelog.
- Remove primitive-specific resource/anatomy rules that are no longer needed, or rename them to policy rules if the child directory remains `primitives/` temporarily.
- Update performance budgets, mutation/fuzz tests, inventory, README, contributor docs, and release checks.
- Keep failure isolation, bounded config, safe local-resource reads, and trigger fuzz coverage.

### Compatibility decision gate

Before removing `/scaffold primitive`, confirm whether the next release permits this documented breaking change. If not, retain the command for one release but make it emit only a deprecation error/instruction and generate nothing.

### Focused verification

```text
node --experimental-strip-types --test test/pi-primitives.test.ts test/pi-primitives-fuzz.test.ts test/pi-primitives-mutation.test.ts
node --experimental-strip-types --test test/pi-commands-scaffold.test.ts
npm run check:anatomy
npm run check:performance
npm run typecheck
```

### Exit criteria

- No `whimsical` runtime module exists.
- Three policies share one bounded trigger/injection implementation.
- No scaffold path encourages new nested plugins.
- Existing package filters for `extensions/pi-primitives` continue to work.

## Phase 6B — Optional major-version rename to `pi-policies`

Do this only in a release that can intentionally change package filter paths.

### Tasks

- Move `extensions/pi-primitives/` to `extensions/pi-policies/`.
- Rename config/status/documentation identifiers after deciding whether config migrates from `pi-primitives` or remains stable.
- Update `profiles/core.json`, `profiles/full.json`, package resources, generated inventory, docs, scripts, tests, and performance checks.
- Publish explicit migration instructions for user settings that filter `extensions/pi-primitives`.
- Do not ship both old and new extension folders because `./extensions` discovery would load both.

### Exit criteria

- No stale `pi-primitives` path remains outside migration documentation.
- Profile fixtures and package discovery checks pass.
- A clean install loads each policy once.

## Suggested change/PR slices

1. `chore: enforce extension dependency boundaries`
2. `refactor: extract git snapshot service`
3. `refactor: extract context snapshot contract`
4. `refactor: share swe todo docket ui`
5. `refactor: centralize artifact publication`
6. `refactor: move scaffold templates to commands`
7. `refactor: narrow primitives to policies`
8. `docs: document extension service boundaries`
9. Optional major release: `refactor: rename pi-primitives to pi-policies`

Avoid combining the snapshot, UI, artifact, and policy migrations into one change; each has a different regression surface and rollback path.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Shared services become a new monolith | Small typed contracts, no registration side effects, separate folders and tests |
| HUD behavior changes during extraction | Characterization tests first; move logic before simplifying it |
| Shared UI leaks lifecycle behavior | UI emits intents only; no session/file/service imports |
| Artifact refactor weakens path safety | Shared safety matrix, adversarial symlink/collision tests, explicit `workflow.json` denial |
| Template move alters generated output | Golden byte comparisons for every scaffold kind |
| Primitive removal breaks user filters/config | Keep extension path in 6A; recognize deprecated `whimsical`; gate physical rename to major release |
| Architecture checker blocks legitimate tests | Scan production extension source only; test imports remain outside the rule |
| Temporary allowlist becomes permanent | Exact-file/import allowlist that fails when stale; mandatory removal in Phase 2 |

## Rollback boundaries

- Phase 1 can be reverted independently.
- Phase 2 rollback restores internal import locations without state migration.
- Phase 3 rollback restores presentation modules; no persisted state changes.
- Phase 4 rollback must preserve already-created artifacts; formats and paths do not change.
- Phase 5 rollback restores template paths; generated project output remains compatible.
- Phase 6A rollback may restore policy host behavior; deprecated config parsing ensures old settings remain readable.
- Phase 6B requires documented package-filter rollback because settings paths change.

## Decisions required before implementation

1. **Breaking-change window:** may `/scaffold primitive` be removed in the next release, or must it first become a deprecation-only command?
2. **Physical rename:** approve or defer `pi-primitives` → `pi-policies`. Recommended: defer to a major release.
3. **Context JSON:** confirm `/pi-context json` remains supported. This plan preserves it through a typed system-JSON artifact operation.
4. **Shared path naming:** approve `src/contracts`, `src/services`, and `src/ui/docket-kit`, or choose equivalent package-level names before Phase 2.
