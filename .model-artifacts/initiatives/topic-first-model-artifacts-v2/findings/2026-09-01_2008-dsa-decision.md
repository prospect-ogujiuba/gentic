# DSA Decision: Deterministic Relocation and Reference Closure

- Topic: `topic-first-model-artifacts-v2`
- Reviewed spec: `.model-artifacts/initiatives/topic-first-model-artifacts-v2/specs/2026-09-01_2008-initiative-spec-r1.md`
- Reviewed plan: `.model-artifacts/initiatives/topic-first-model-artifacts-v2/plans/2026-09-01_2008-plan-index-r1.md`
- Decision: accept with plan revision required

## Problem summary

The migration must map a bounded file tree from v1 to v2, find exact inbound path references, order structured hash rewrites, detect conflicts, and support deterministic recovery. Semantic requirements are exactness, one-to-one relocation, stable ordering, reference closure, collision refusal, bounded memory, and recoverable persistence. Faster scans are secondary.

## Current implementation

pi-artifacts walks `.model-artifacts`, stores discovered entries in arrays/sets, protects manifest/index authority, builds a reference trie over known source paths, scans repository files, sorts migration moves, fingerprints stable JSON, and applies rename-oriented transactions. This is an adequate standard-library baseline, but current classification treats protected kind-first authority as non-migratable and transactions do not model full graph rewrites and retained transformed/original bytes.

## Workload / constraints

- Dominant operations: one bounded recursive inventory; exact old-path lookup; reference matching across bounded repository files; collision/mixed-topic checks; deterministic sort; structured JSON/hash dependency rewrite; journal lookup during recovery.
- Scale/growth: configured maximum files/bytes; expected repository-scale, not unbounded service traffic. Evidence is inferred from current fail-closed inventory limits and tests, not measured production telemetry.
- Read/write: plan is read-heavy; apply writes each affected artifact once plus journal/rollback payload.
- Ordering: byte-stable plan fingerprints and dependency-safe transforms are semantic.
- Persistence/concurrency: exclusive claim and crash recovery required; no concurrent migrations.
- Memory: O(number of paths + total bounded scanned bytes) is acceptable only under explicit existing/new budgets.

## Recommendation

Keep standard-library structures:

1. A sorted array of inventory entries remains the deterministic iteration source.
2. A `Map<oldPath,newPath>` is the authoritative relocation table; build a reverse `Map<newPath,oldPath>` (or set) for one-to-one/collision validation.
3. Reuse the reference trie for single-pass exact candidate matching; do not run one repository scan per moved path.
4. Represent structured hash dependencies as a sparse adjacency list plus indegree map and use topological sort with cycle detection. Leaves/spec revisions hash first; indexes/pointers that embed those hashes follow. Any cycle is a planner blocker.
5. Persist an append-only transaction journal with named states and a manifest of rollback payload fingerprints. Treat staged/transformed bytes and retained originals as files, not in-memory/base64 ledger blobs.
6. Sort all externally fingerprinted arrays by normalized path/ID before stable JSON serialization.

## Rejected alternatives

- Repeated `find`/string replacement per relocation: O(P×B), risks overlaps and nondeterminism.
- General graph database or specialized tree: no scale evidence and creates packaging/migration complexity.
- One giant JSON ledger containing base64 originals: high peak memory, poor locality, and brittle bounds.
- Blind global replacement: violates exact-reference semantics and can corrupt unrelated prose.
- In-place hash rewrites without dependency graph: risks stale pointers and irrecoverable intermediate authority.

## Complexity impact

For F discovered artifact paths, R repository bytes scanned, P relocated paths, and E structured hash dependencies:

- Inventory/sort: O(F log F).
- Relocation lookup/collision validation: expected O(P) using maps, versus repeated O(P×F) scans.
- Reference matching: O(R + matches) using the trie.
- Hash ordering: O(P + E) topological sort.
- Staging/apply: O(total affected bytes).

Practical constants remain simple standard-library operations.

## Memory tradeoff

Maps, trie nodes, adjacency lists, and staged metadata duplicate normalized path strings: O(P + E). File payloads stay on disk under configured transaction byte limits. Preserve current max-file/max-byte guards and add explicit rollback/staging budgets before allocation or copy.

## Migration advice

Add representations behind current pi-artifacts domain boundaries. Keep inventory and plan immutable after fingerprinting. Preflight proves bijection, reference closure, dependency acyclicity, free destinations, and storage budgets. Publish only a fully validated staged graph. Retain original bytes until explicit finalize. Rollback must compare current fingerprints before restore.

## Validation plan

- Table/property-style tests for one-to-one mapping, sorted stability, collision and cycle rejection.
- A fixture with nested manifest/index/hash references proving topological rewrite correctness.
- A single-scan reference-matching test with overlapping path prefixes.
- Bound tests for files, bytes, staging, and rollback payload.
- Failure injection at every journal state, byte-identical rollback comparison, and re-entry idempotence.
- Measure scan/stage duration on Gentic before changing structures further; no benchmark-driven specialization is currently justified.

## Confidence

High for standard-library representation and deterministic graph ordering based on inspected code and semantic requirements; medium for operational size budgets until Gentic and DevArch audits provide measured cardinality/bytes.
