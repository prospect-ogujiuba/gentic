## Problem summary

The runner needs deterministic stage ordering, exactly-once continuation, scoped retries, and crash recovery. These are semantic correctness requirements, not throughput optimization.

## Current implementation

`domain/lifecycle.ts` already supplies transition tables, blocked cases, canonical retry keys, `evaluateAutonomousRunnerStep`, and stable-state reconstruction. `orchestrate.ts` already selects a gate-aware next stage. Runtime persistence stores a single canonical initiative cursor atomically. There is no active event-driven runner, dispatch lease, or structured stage checkpoint.

## Workload and constraints

- Dominant operations: read one run, validate one event, append/replace one attempt, and choose one next action.
- Scale: one active runner per topic, tens rather than millions of attempts.
- Ordering: strict serial order; parallel stage dispatch is invalid.
- Persistence: bounded JSON state in repository-local system logs.
- Concurrency: duplicate `agent_settled`, restart, or multiple sessions are correctness hazards.
- Evidence quality: implementation structure and event semantics are inspected; real-world attempt volume is inferred and deliberately bounded.

## Recommendation

Use one versioned normalized JSON runner record keyed by topic, with scalar `runId`, owner/lease token, monotonic `dispatchSequence`, current dispatch token, exact plan/contract identity, policy, budget counters, checkpoint state, and terminal reason. Reuse existing transition and retry functions. Derive tokens from run identity plus sequence and canonical contract/stage identity; compare exact strings rather than scan logs. Persist the whole small record through atomic temp-write/fsync/rename. Maintain at most one pending dispatch and one accepted checkpoint.

Use a pure reducer:

`(persisted runner, fresh canonical inspection, checkpoint/event) -> decision + next persisted runner`

The side-effect controller may act only after the reducer returns a validated action and the updated pending-dispatch state is durably written.

## Rejected alternatives

- **Unbounded append-only event log as authority:** improves forensics but makes reconstruction and partial-write recovery more complex; keep optional logs as evidence, not runner authority.
- **Queue of multiple future skills:** violates fresh canonical reinspection and permits stale work.
- **Map of parallel topic runners in one process:** unnecessary initially and complicates ownership; serialize one active runtime runner while allowing separate inert topic state files.
- **Assistant prose parsing:** not a data structure with enforceable identity or schema.
- **Database/SQLite:** no evidenced volume or query need.

## Complexity impact

All dominant runner operations remain O(1); canonical contract readiness remains the existing O(V+E) graph inspection. Recovery reads one bounded state file plus canonical artifacts. Memory is O(1) per active runner plus bounded diagnostics/retry keys.

## Memory, ordering, and persistence tradeoff

A snapshot record loses a full attempt history, so durable reports/logs retain human evidence while the runner record retains only bounded recent diagnostics and counters. Serial monotonic sequencing makes duplicate detection simple. Atomic replacement and owner-token validation are mandatory; last-writer-wins without ownership is rejected.

## Migration advice

Use a new runner-state version independent of existing cursor envelope versions. Absence means no run. Unknown versions, owner mismatch, or pending-dispatch/checkpoint contradiction block resume. Rollback ignores the additive file. Do not auto-reap an owner token solely by elapsed time; require explicit operator recovery when liveness is uncertain.

## Validation plan

Table-test reducer transitions and identity validation. Use temporary repositories for atomic round trip, partial/corrupt state, future version, symlink/path escape, duplicate event, restart between persist and send, and restart between checkpoint and continuation. Add a deterministic stress test over repeated duplicate settled/checkpoint events; no benchmark is needed unless state exceeds configured bounds.

## Confidence

High for the normalized single-record/reducer design because scale is bounded and correctness requires serialization. Medium for SDK event interleavings until fake-event and fresh-session E2E tests confirm them.
