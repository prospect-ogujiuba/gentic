## Goal

Implement a non-mutating request resolver that selects one exact active canonical contract, derives all redundant low-level arguments, and validates one exact review→verification evidence chain before returning the existing `CompleteCanonicalContractRequest`.

## Observable behavior

- An explicit valid topic/contract resolves against the active manifest/index.
- Omitted topic resolves only when canonical repository resolution yields exactly one active initiative; omitted contract resolves only from that manifest's `activeContract`.
- One fully current approving review produces a request containing the active plan revision, stable contract path, recomputed contract hash, recomputed review hash, and review-bound recomputed verification hash.
- Missing, inactive, malformed, stale, unsafe, incomplete, oversized, or ambiguous state produces a structured non-mutating rejection with the affected artifact/scope.

## Scope and non-goals

### Scope

- Add an exported typed resolver adjacent to completion or in one focused completion-resolution module.
- Reuse/refactor the strict closed-envelope parser so resolver and transaction enforce identical envelope shapes.
- Use `inspectCanonicalInitiative`/canonical resolution for current state, then independently recompute bytes used in the derived identity.
- Add bounded direct-child report enumeration: sorted, no symlinks, maximum 200 entries, maximum 2 MiB per file, maximum 16 MiB aggregate bytes.
- Add behavior-first resolver tests and retain existing transaction tests.

### Non-goals

- No transaction, journal, completion-record, manifest/index schema, or low-level command behavior change.
- No newest/oldest review preference, recursive report search, todo/chat preference, evidence generation, or recovery automation.

## Dependencies and entry inputs

- Dependencies: none.
- Entry inputs available: active spec/plan, current `completion.ts`, `planning.ts`, Pi-SWE evidence envelopes, TDD finding, and cross-cutting finding.
- Required capability: local bounded filesystem inspection and SHA-256 hashing already used by pi-swe.

## Expected files/outputs

- `extensions/pi-swe/src/completion.ts` for exported shared strict envelope parsing only if required.
- `extensions/pi-swe/src/completion-resolution.ts` (preferred if separation keeps mutation code stable) with typed request/result and bounded resolver.
- `test/pi-swe-completion.test.ts` fixtures/tests; a focused new test file is acceptable only if it reduces fixture coupling.

## Specialist decisions incorporated

- **TDD:** first Red proves missing registration separately, then resolver selection, identity, unique review, evidence chain, bounds, and delegation behaviors; no plan-time Red claim.
- **Security:** closed envelopes; exact current identity; direct regular files only; no symlink traversal; count/per-file/aggregate bounds; duplicate rejection independent of chronology/downstream validity.
- **Operations:** derivation is non-locking; the unchanged transaction re-inspects under its exclusive claim and rejects derivation-to-mutation drift.
- **Compatibility:** construct the existing request type; retain command/API and schema behavior.

## Acceptance criteria

1. Explicit topic and contract resolve only when active and indexed; omitted fields infer only one canonical initiative and its one manifest active contract.
2. Current contract bytes are SHA-256 hashed and equal the active index binding before a request is produced.
3. Review scan is deterministic, direct-child, regular-file-only, non-symlink-following, and bounded at 200 entries, 2 MiB/file, and 16 MiB aggregate.
4. Candidate matching requires exactly one strict implementation-review envelope bound to current topic, contract ID/path/hash, plan revision, approve decision, and zero blockers. Zero/multiple matches reject; timestamps and downstream validity never break ties.
5. The selected review bytes are hashed. Its verification reference must be a safe same-topic report path with the declared hash; verification bytes are hashed and its strict envelope must match current identity with `outcome: pass` and `gaps: none`.
6. All rejections are typed, bounded, actionable, and cause no manifest/index/journal mutation.
7. Success returns the unchanged full request with caller-selected `clear|advance`; a later transaction guard remains authoritative for races.
