# Initiative Spec: Topic-First Model Artifacts v2

- Topic: `topic-first-model-artifacts-v2`
- Revision: 1
- Created: 2026-09-01T20:08:18Z
- Predecessor: none
- State: planning

## Problem

Gentic currently stores durable model artifacts by kind first (`.model-artifacts/<kind>/<topic>/...`). A single initiative is therefore fragmented across unrelated top-level buckets, while generated paths, canonical pi-swe authority, migration transactions, tests, documentation, and injected instructions all encode the old layout independently. Moving one repository ad hoc would create split authority and incompatible writers/readers.

## Outcome and observable behavior

Gentic adopts one versioned layout contract atomically:

```text
.model-artifacts/
  initiatives/<topic>/
    specs/
    plans/
    todo/
    findings/
    reports/
    logs/
  system/
    logs/
    reports/
```

After rollout:

1. Initiative artifacts generated by Gentic are written only beneath `.model-artifacts/initiatives/<topic>/<kind>/`.
2. Non-initiative migration and runtime artifacts are written only beneath `.model-artifacts/system/logs/` or `.model-artifacts/system/reports/`.
3. pi-swe discovers one manifest at `.model-artifacts/initiatives/<topic>/specs/manifest.json`; its exact path pointers and contract roots remain hash-validated.
4. Existing kind-first repositories remain readable long enough to produce and execute an explicit migration, but a topic present in both layouts is a deterministic blocking conflict rather than split authority.
5. A reviewed migration relocates a complete initiative, rewrites exact internal `.model-artifacts/...` references and machine indexes, refreshes affected hashes, and supports rollback from retained transaction evidence.
6. `docs/plans/` remains curated, stable, human-facing documentation and never duplicates a canonical generated plan.
7. Gentic is updated and verified before DevArch is migrated once with the released migration workflow.

## Users

- Gentic extension authors maintaining pi-primitives, pi-todo, pi-swe, pi-artifacts, pi-context, packaging scripts, and tests.
- Coding agents creating, discovering, reviewing, and executing canonical initiative artifacts.
- Repository maintainers migrating existing Gentic and downstream DevArch artifact histories.

## Constraints

- Production path semantics must change in one reviewed Gentic change set; no extension may ship a v2 writer while another active extension only understands v1.
- Runtime extensions remain standalone; pi-artifacts must not import pi-swe or pi-todo internals.
- The layout contract is declarative and conformance-tested; each standalone extension may keep a small local path adapter.
- All paths are project-relative, normalized POSIX paths with kebab-case topic segments and no traversal, absolute paths, or symlink escapes.
- Initiative kinds are exactly `specs`, `plans`, `todo`, `findings`, `reports`, and `logs`. System kinds are exactly `logs` and `reports`.
- Generated artifact filenames retain `YYYY-MM-DD_HHMM-<short-name>.md`; canonical pi-swe filenames and `manifest.json`/`contracts.json` remain stable exceptions.
- Canonical spec and plan revisions remain immutable. Migration may relocate and mechanically rewrite them only as one audited repository transformation, preserving revision identity and recording old/new hashes.
- Bounds, deterministic ordering, collision refusal, fingerprints, exclusive transaction claims, and rollback protections from pi-artifacts remain fail-closed.
- Migration never follows symlinks and never silently classifies ambiguous artifacts.
- No production implementation occurs during this planning workflow.

## Non-goals

- Redesigning todo semantics, pi-swe lifecycle states, contract graph semantics, or review policy.
- Making `docs/plans/` a generated-plan mirror.
- Automatically migrating a repository on package installation or first access.
- Migrating DevArch before the Gentic implementation, migration engine, and release verification pass.
- General-purpose rewriting of arbitrary user prose that merely resembles a path.
- Introducing a shared runtime dependency that couples otherwise standalone extensions.

## Compatibility and rollout

- Name the new contract **model-artifacts layout v2**.
- pi-swe manifest schema advances to v2 so layout authority is explicit; a v1 manifest is legacy-readable but not writable in place.
- Readers accept either a complete v1 topic or a complete v2 initiative during the transition. If both exist for the same topic, inspection and execution block with a migration-conflict diagnostic.
- Writers emit v2 only. When a requested topic exists only in v1, writers return a migration-required repair instead of creating a parallel v2 tree.
- Migration plans are explicit, reviewable, fingerprinted, bounded, and apply only when sources and references still match plan-time fingerprints.
- Rollout order: land all Gentic code/tests/docs atomically; use the verified command to migrate Gentic's own tree; release/consume the updated package; audit, plan, review, apply, and verify DevArch once.

## Migration and rollback

- The migration planner derives a deterministic old→new relocation table for complete initiative trees and eligible system artifacts.
- Preflight blocks mixed-layout topics, collisions, invalid files, unresolved references, stale fingerprints, unsupported manifests/indexes, and size/count bound violations.
- Apply uses an exclusive claim, a transaction ledger, staged transformed bytes, and retained rollback payloads. It updates exact references, manifest pointers/schema, contracts indexes, and all affected content hashes before publishing destinations.
- Recovery is idempotent after interruption. Rollback restores original bytes and paths only when post-apply fingerprints still match; otherwise it refuses destructive overwrite.
- A separate finalize action may remove retained rollback payloads after verification; finalization is never implicit.

## Risks

- Recursive hashes and cross-file pointers can become inconsistent if rewrite order is not defined.
- Broad string replacement can corrupt unrelated prose or miss encoded references.
- Moving transaction logs while a transaction is active can make recovery unreachable.
- Dual-read support can accidentally become indefinite compatibility debt.
- Existing external scripts may depend on old paths without being discoverable in this repository.
- Large repositories may exceed current inventory limits or rollback storage budgets.

## Acceptance criteria

- **AC1:** The injected convention and public docs define only the v2 initiative/system layout and the `docs/plans/` source-of-truth boundary.
- **AC2:** pi-todo creates and validates initiative artifacts at v2 paths and rejects mixed, unsafe, wrong-kind, and legacy-write paths with actionable repairs.
- **AC3:** pi-swe schema-v2 manifests, discovery, plan/contract validation, completion, orchestration, and reports operate at v2 paths; v1-only topics are read-only/migration-required and mixed topics block.
- **AC4:** pi-context, lifecycle/runtime ledgers, packaging/resource validation, release scripts, and other Gentic-owned consumers emit or recognize the correct v2 initiative/system paths.
- **AC5:** pi-artifacts deterministically audits v1 and v2, plans complete kind-first→topic-first relocation, refuses ambiguous/stale/colliding/mixed states, and writes its own records beneath `system/logs`.
- **AC6:** apply, recovery, rollback, and finalize preserve bytes and authority under interruption and post-apply modification safeguards, including reference and hash rewrites.
- **AC7:** Focused unit/integration tests, the full test suite, resource checks, and release verification pass with v2 fixtures and explicit v1 compatibility cases.
- **AC8:** Gentic's existing artifact tree is migrated once from a reviewed plan and passes a post-migration audit with no canonical v1 initiative authority remaining.
- **AC9:** A DevArch operator handoff identifies prerequisites, dry-run evidence, rollback retention, and the single approved migration sequence; DevArch migration does not begin before Gentic verification.

## Open blockers

None for planning. Implementation approval must bind an exact reviewed plan revision. DevArch execution remains gated on the released and verified Gentic migration workflow and a repository-specific audit.
